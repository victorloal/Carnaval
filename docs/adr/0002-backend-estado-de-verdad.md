# 0002. Ingestion backend with the database as the source of truth

- **Status:** Accepted
- **Date:** 2026-10-03
- **Relates to:** brief §6 decisions 1 and 2, §7 (architecture), §14 (risks)

## Context

The information needed for the site exists in two fragile places: the official WordPress
site `carnavaldepasto.org` and a PDF of the schedule. Neither is stable. The markup
changes yearly, there is no public API, and the whole schedule changes once per year.

Two tempting designs:

1. **Static JSON files** committed to the repo, regenerated by a script.
2. **A live scraping backend** that the frontend queries.

Option 1 is simple but makes the scraper a hard dependency of the deploy: if extraction
breaks, either the site shows stale data with no way to fix it, or the deploy fails.
Option 2 risks the opposite — a runtime dependency on a third-party site that can be slow,
rate-limited, or down, which would take the public site down with it.

## Decision

A **backend that collects data, with the database as the source of truth**. The scraper
only ever *proposes* changes.

Pipeline:

```
Sources (WP REST API → HTML → PDF)
  → EXTRACT → raw_documents (raw payload + content hash)
  → TRANSFORM → schema validation
  → STAGING (status = pending)
  → human review
  → LOAD (upsert into published tables)
```

Invariants, all of which are requirements rather than aspirations:

- **Idempotent.** Running the pipeline twice must not duplicate data. Content hashes gate
  reprocessing: unchanged input is skipped entirely.
- **Nothing is published without review.** Every record enters as `status = pending`.
  A human moves it to `published` or `rejected` (with `rejection_reason`). Admin-configured
  auto-publish rules are permitted but off by default.
- **Full traceability.** Every record stores `origin` (`scraped` | `manual` | `community`),
  plus the `ingestion_run` id or the user id that produced it.
- **Failure never degrades published data.** If a scrape fails, nothing already
  `published` is deleted or modified. The site keeps serving.
- **The scraper is optional.** The admin can create and edit every record by hand. Losing
  the scraper costs convenience, not availability.
- **Resilience.** Retries with exponential backoff; after N consecutive failures a source
  is auto-disabled and an alert is raised. The admin panel shows each source's status and
  last successful run.

## Consequences

**Positive**
- The public site's availability is independent of any third party.
- Human review catches extraction errors before the public sees them, which is what makes
  the "pending → published" moderation model meaningful.
- Hash-based change detection makes routine runs cheap, which matters on free-tier
  infrastructure and rate-limited sources.

**Negative**
- Content is not live: publishing requires a manual step. For a schedule that changes
  yearly this is an acceptable cost; for a real-time feed it would not be.
- Raw document storage grows. Mitigation: retention policy per source, and raw payloads are
  never committed to git.
- Two writes (staging, then published) instead of one. Accepted: it is the price of review.

## Alternatives considered

- **Static JSON in the repo.** Rejected: no manual-edit escape hatch, and the scraper
  becomes a deploy-time dependency.
- **Live scraping at request time.** Rejected: couples public availability to a
  third-party site and makes rate-limiting and caching someone else's problem.
