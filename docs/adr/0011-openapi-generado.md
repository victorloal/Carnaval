# 0011. The OpenAPI contract is generated, not hand-written

- **Status:** Accepted
- **Date:** 2026-10-03
- **Relates to:** brief §17 (`docs/02-diseno/openapi.yaml`), §5 (objective 5), ADR 0009

## Context

Brief §17 lists `openapi.yaml` as a **design** artefact, produced in the design phase
(step 3) before implementation. That implies a design-first workflow: the contract is
written by hand, reviewed, and the backend is then built against it.

With Django REST Framework, the alternative is to derive the schema from the serializers
and views with `drf-spectacular` and commit the generated file. The brief's intent is
that the API is *documented*; it does not require that the document be authored by hand.

## Decision

**The contract is generated by `drf-spectacular` from the DRF serializers and committed
to `docs/02-diseno/openapi.yaml`.**

- Developers annotate serializers and views (`@extend_schema`) where the auto-generated
  description would be unclear.
- CI regenerates the file and **fails the build if it differs from the committed copy**.
  This makes the contract a reviewable, diffable artefact — it is versioned and changes
  only through review — while being impossible to let drift.
- The React client is generated from the same contract, so frontend types cannot disagree
  with the backend.

## Consequences

**Positive**
- The contract cannot go stale. A hand-written contract silently rots the first time a
  serializer changes, and the drift is invisible until something breaks.
- Committed and diffed, so contract changes are still reviewed in a pull request. This
  preserves the reviewability that justified design-first.
- One source of truth for both documentation and client types.

**Negative**
- **The contract is no longer available before the code exists.** Design reviews of the
  API surface must happen against prose and the data model instead, and any change to the
  API implies a code change before the contract can be reviewed. This is a genuine loss
  compared to design-first and is accepted knowingly.
- `drf-spectacular`'s output needs curating to read well; sloppy annotations produce a
  technically valid but unhelpful document.
- Generated files invite accidental hand-editing. The CI drift check makes that fail
  loudly rather than silently.

## Alternatives considered

- **Hand-written `openapi.yaml`, design-first.** Rejected: guaranteed drift between
  contract and implementation, with no mechanical check to catch it.
- **Serve the schema only, commit nothing.** Rejected: loses version history and review of
  API changes, which is the main benefit of having the file in the repo at all.

## Note

If the project ever needs an API consumed by a third party before the backend is built,
this ADR should be revisited — that is the one case where design-first is correct.
